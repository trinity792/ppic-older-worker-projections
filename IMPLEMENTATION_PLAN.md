# Older Worker Projections Migration Implementation Plan

## Outcome

Replace the ignored, read-only `v0/` implementation with a production site at the repository root that lets readers compare California older-worker historical data and projections, inspect the same prepared results in an accessible table, and download those results. The site will use Vite, React, TypeScript, npm, visx, and a static Vercel deployment.

The migration will preserve the legacy product rules while adopting a focused subset of the sibling `../web-data-visualization` project's visual language: PPIC typography and color, editorial hierarchy, compact controls, white chart surfaces, restrained borders and shadows, clear chart notes, and consistent axis and legend styling. The sibling project remains a read-only reference; no code will be imported as a package or edited in place.

This remains a single-purpose line-chart interactive. A chart builder, module registry, generalized visualization schema, broad UI kit, application navigation, user accounts, saved views, dark mode, server-side rendering, and chart-image export are out of scope. `ChartFrame` should be reusable inside this project, but it should not become a general charting platform.

## Implementation status

The root skeleton exists with Vite, React, TypeScript, granular visx packages, Vitest, React Testing Library, Playwright, ESLint, Vercel configuration, centralized CSS tokens, and component/chart/data seams. Workstreams 3-9 are now implemented: the CSV parser, the calculation pipeline, comparison state and controls, the design foundation, the visx chart, the table/view-toggle/CSV export, and a responsive/accessibility hardening pass. `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:e2e`, and `npm run test:python` all pass; see `README.md` for the verified command list and `agents/memories/2026-09-18-implementation-workstreams.md` for what was built and non-obvious discoveries. Workstream 10 (README/CLAUDE.md commands, `vercel.json` immutable-asset caching) is largely done; an actual Vercel deployment has not been performed.

Workstream 1 is complete: ten browser-captured parity fixtures now live in `tests/fixtures/parity/`, generated by a reusable Playwright script (`capture-legacy-fixtures.mjs`) driving the real, unmodified `v0/` app. See `tests/fixtures/parity/README.md` for the fixture list, capture method, and findings the CSV-contract approval gate and workstream 8 should account for (the raw-mode CSV label misdescribes its own units, and `v0`'s download button never disables itself even when every comparison is suppressed).

The requested data pipeline uses `public/data/raw/` for the unchanged source export and `public/data/cleaned/` for the deterministic browser asset. Standard-library Python scripts remove only the unnamed export-index column, validate the structural contract, preserve all analytical values and missing tokens, write atomically, and prove raw/cleaned parity with a semantic SHA-256 digest. The current source contains 15,083 rows, 38 analytical columns after index removal, and 17 finite negative projected `totpop` values; those values are reported and preserved because the legacy calculation accepts them.

## Current state

- The repository root now contains the migration scaffold and verification configuration. Placeholder calculation seams make incomplete domain behavior explicit rather than simulating results.
- `v0/index.html`, `v0/styles.css`, and the 1,202-line `v0/app.js` form a static, framework-free implementation. `v0/` is read-only and ignored by Git.
- The legacy app loads `v0/data/projections_age5cat_2006_2040.csv`, a roughly 7 MB file containing 15,083 records and 39 columns. It spans 2006–2040; historical rows cover 2006–2024 and projected rows cover 2020–2040.
- One comparison is present initially. Readers can add and remove comparisons, choose an outcome, filter by race/ethnicity, gender, age, and education, change supported outcome denominators, and display percentages or derived raw numbers.
- The ten exposed outcome families are labor force participation, full-time work, foreign-born status, living with family, living with a spouse, poverty, near poverty, homeownership, housing costs above 30 percent of income, and housing costs above 50 percent of income. Outcome availability is derived from the CSV headers.
- Rows are matched through legacy categorical mappings and precedence rules. The combined age selections `55-64` and `65 and older` are computed from the five-year categories. Race/ethnicity uses the precedence Latino, White, Black, Asian, Pacific Islander, then Other/None Listed. The legacy control omits Pacific Islander, but the migrated control includes it as an approved intentional difference; a full-period Pacific Islander comparison is expected to be suppressed because its 2006 and 2007 populations are below 20,000.
- Aggregation groups rows by numeric year and `pred`, sums `totpop`, excludes missing outcomes from the valid weight, and calculates `sum(outcome * totpop) / validWeight`. Missing numeric values are represented as missing rather than zero.
- A comparison is hidden everywhere when any positive historical or projected population represented by that comparison is below 20,000. Zero-population buckets are treated as no data rather than suppressed.
- Historical 2020 poverty and near-poverty values can be linearly interpolated only when the 2020 point exists and is missing, its population is positive and not suppressed, and the adjacent sorted historical points are present, valued, and not suppressed.
- Historical and projected lines share a comparison color and use solid and dashed strokes respectively. Missing points break lines. Interpolated percentage segments use a dotted cue. The chart uses hover tooltips, while the table is the non-visual data alternative.
- The sibling reference is a much larger Next.js/Tailwind/Plotly application. Relevant patterns include its PPIC color ramps, Source Sans 3/Source Serif 4/Inter typography roles, pill actions, white cards with restrained borders, segmented chart/data toggle, 2 px data lines, 1 px axes and grids, horizontal-only grid lines, responsive note fitting, and compact chart legends. Its framework breadth, Radix/shadcn component collection, Plotly runtime, module system, editors, and export system should not be copied.

## Decisions

### Confirmed

- Application: Vite + React + TypeScript.
- Package manager: npm with a committed lockfile.
- Chart rendering: visx/D3 primitives rendered as React SVG, with a shared project-local `ChartFrame` and a small line-mark layer.
- Hosting: static Vercel deployment from Vite's `dist/` output.
- Data layout: an unchanged source export in `public/data/raw/` and a deterministic, validated serving file in `public/data/cleaned/`, generated by standard-library Python scripts.
- Race/ethnicity filter: include Pacific Islander by mapping the existing `pacis` field; retain the legacy whole-comparison suppression rule, so the option may produce a suppression message rather than visible values.
- Source of behavior and calculations: `v0/`, constrained by `AGENTS.md` and `agents/skills/data-integrity.md`.
- Source of visual direction: selected patterns from `../web-data-visualization`, without adopting its Next.js, Tailwind, Plotly, or platform architecture.

### Recommended implementation choices

- Use plain project CSS with centralized custom-property tokens rather than adding Tailwind or copying the reference UI library. Native HTML controls are sufficient for this focused interface and provide the best semantic baseline.
- Install only the visx packages used by the line chart, expected to include scale, shape, axis, grid, group, responsive measurement, tooltip, and text utilities. Do not install the all-in-one package if granular packages produce a smaller and clearer dependency set.
- Use Vitest for pure and component tests, React Testing Library with `user-event` for interactions, and Playwright for narrow/wide browser flows, downloads, keyboard checks, and a small visual-regression set.
- Keep data parsing, selection normalization, aggregation, suppression, interpolation, display-value preparation, formatting, and CSV serialization as pure TypeScript modules. React components should consume one serializable prepared-result model rather than recalculate values.
- Load the CSV at runtime as a static asset so the initial JavaScript bundle does not contain 15,083 records. Show explicit loading and failure states.
- Use a single-page application without a router. Add `vercel.json` only for settings that Vite and Vercel cannot infer, such as deliberate cache headers.

### Approval gate before implementation (resolved)

1. **CSV download contract — resolved: the new contract.** The legacy file always exports underlying rates in columns named `*_value`, even when the table is showing derived raw numbers, and it does not export an interpolation flag; the parity fixtures additionally found that raw mode's own label claims "raw count" while still exporting the untouched rate. The user approved the recommended migration behavior: export the displayed value and unit plus explicit status/interpolation metadata from the shared prepared result, implemented in `src/data/exportDisplayedData.ts`. This intentionally breaks byte compatibility with the legacy CSV headers/values; see `agents/memory.md`.

## Workstreams

### 1. Freeze the legacy contract and record representative outputs

Before scaffolding changes can obscure behavior, document the current options, defaults, labels, data statuses, table cells, and CSV fields. Run `v0/` from a read-only local server and use a browser characterization script to drive representative selections and capture small committed parity fixtures; do not modify legacy files or commit the full legacy site.

Characterization cases must include the statewide default, one comparison using every filter, the two combined age groups, a denominator-switching outcome in both modes, multiple comparisons, percent and raw display modes, a comparison suppressed by one low-population year, no matching rows, missing values, and valid 2020 poverty interpolation. Record the legacy omission of Pacific Islander and verify the approved migrated option maps only `pacis=TRUE` rows before whole-comparison suppression is applied. Record the current raw-mode CSV mismatch as known behavior, not an accidental implementation requirement.

Completion checks:

- Each fixture identifies its selection, expected comparison label, years, actual/projected values, populations, and status metadata.
- Values are captured from behavior backed by `v0/app.js`, not inferred from screenshots.
- The baseline explains every intentional difference proposed for the new implementation.

### 2. Scaffold the minimal React application and verification toolchain

Create the Vite React TypeScript application at the repository root without touching `v0/`. Add strict-enough TypeScript settings to catch unchecked data access, npm scripts for development, build, preview, lint, type checking, unit/component tests, and Playwright, and a committed `package-lock.json`. Keep dependencies limited to React, the chosen granular visx packages, and the agreed test/lint tooling.

Create a shell page that builds and renders on a local Vite server, then verify a Vercel preview can serve a deep refresh of the single route and static assets. Do not add routing, server APIs, global state libraries, Tailwind, or a component framework.

Completion checks:

- A clean `npm ci` followed by lint, type checking, tests, and `npm run build` succeeds.
- The production bundle contains no Plotly, Next.js, Tailwind, or unused visx umbrella dependency.
- The Vercel preview serves `index.html`, hashed application assets, and the selected data URL over HTTPS.

### 3. Establish the canonical data asset and validated parser

Use the approved raw/cleaned pipeline and expose only the cleaned file as the browser's production CSV URL. Keep analytical source fields and values unchanged; the cleaner removes only the unnamed export index. Parse headers first, require the documented structural columns, determine which outcome definitions are selectable from available columns, and convert only `year`, `totpop`, and known outcome fields to numbers. Preserve the source boolean fields and `pred` values as explicit parsed enums rather than relying on truthiness.

Define and test a clear invalid-row policy: reject the load with a named validation error when required columns are absent or when no valid rows remain; skip individual rows with invalid `year` or `totpop` only if the skipped-row count is surfaced in diagnostics and covered by tests. Treat blank, `NA`, and `NaN` outcomes as missing. Ignore the unnamed source index column without rewriting the dataset.

Completion checks:

- The production file parses to 15,083 valid rows, 39 source columns, years 2006–2040, historical years 2006–2024, and projected years 2020–2040.
- Missing poverty values remain `null`; valid zeroes remain numeric zeroes.
- Missing-column, empty-file, malformed-record, invalid-row, fetch-failure, and abort paths produce useful typed errors and visible user messages.
- Tests use tiny hand-authored CSV strings as well as a single integration assertion against the production file.

### 4. Build the pure calculation and prepared-result pipeline

Port the outcome definitions, category mappings, filter matching, comparison labeling, outcome availability, denominator resolution, weighted aggregation, suppression, interpolation, raw-value derivation, sorting, and formatting into pure TypeScript. Keep the functions independent from React, DOM APIs, SVG, and download side effects.

Use explicit types for source rows, parsed rows, comparison selections, denominator mode, prediction status, and point status. The prepared result should contain the human-readable comparison label, color key, resolved outcome and denominator, matched-row count, comparison-level suppression reason, and actual/projected points. Each point should retain year, rate, displayed value, unit, total population, valid calculation weight, and a discriminated status such as `valid`, `missing`, `suppressed`, or `interpolated`.

Apply suppression before producing any renderable or exportable numeric view. A comparison-level suppression result must not retain a public numeric display value that a chart, tooltip, table, accessible summary, or CSV serializer could expose accidentally. Interpolation applies only to 2020 historical poverty outcomes under the exact legacy conditions and must retain its provenance.

Completion checks:

- Hand-calculable tests cover unequal weights and exclusion of missing outcomes from `validWeight` while keeping total population distinct.
- Every filter and filter combination is tested, including `55-64`, `65 and older`, categorical precedence, Pacific Islander mapping, and the expected suppression of the full-period Pacific Islander comparison.
- Denominator tests cover fixed and selectable outcomes in both modes, including state preservation when switching percent/raw views.
- Actual and projected rows remain separate in overlapping years 2020–2024.
- Suppression tests cover 19,999, exactly 20,000, 20,001, zero/no rows, and a comparison where only one year is below the threshold.
- Interpolation tests cover every valid condition and each invalid condition independently, including missing neighbors and suppressed neighbors.
- Prepared results match the representative `v0/` parity fixtures to an agreed numeric tolerance.

### 5. Implement comparison state and semantic controls

Create a reducer or similarly explicit local state model for comparisons, result view, and value format. Start with one statewide labor-force-participation comparison. New comparisons inherit only the previous outcome and denominator, matching `v0/`, while demographic filters reset to All. Preserve valid selections across unrelated control changes and normalize an outcome only when its required columns are unavailable.

Build comparison cards from native labeled selects, fieldsets, legends, radio inputs, and buttons. Show denominator choices only for supported percentage outcomes, retain the chosen denominator while raw values are displayed, and show the poverty source note whenever any comparison uses a poverty outcome. Add/remove actions must update comparison numbering and move focus predictably: new cards receive a meaningful heading or first-control focus, and removal returns focus to the preceding card or Add button.

Completion checks:

- Component tests cover the default state, every control, add inheritance, removal, one-comparison minimum, outcome normalization, denominator visibility, value-format changes, and poverty-note visibility.
- All visible inputs have programmatic labels and grouped radio controls have legends.
- Keyboard users can operate every control, and focus never falls back to the document body after a dynamic removal.
- State transitions call the pure preparation pipeline once and do not duplicate calculations in components.

### 6. Create the focused PPIC design foundation and page shell

Define a small token set for PPIC color ramps, semantic colors, typography, chart colors, spacing, radii, shadows, breakpoints, focus rings, and chart geometry. Use Source Serif 4 for the editorial title, Source Sans 3 for body and section headings, and Inter for controls and chart labels, with resilient system fallbacks and a loading strategy that avoids invisible text. Select a compact accessible series palette from the reference PPIC constants and verify contrast against white.

Replace the decorative beige gradients and translucent oversized panels in `v0/` with the reference project's restrained white/background surfaces, orange brand accent, neutral text hierarchy, thin borders, modest shadows, and compact pill actions. Preserve the report title, explanatory copy, contact information, poverty source, suppression note, denominator meaning, and actual/projected explanation, subject to a final editorial review.

Lay out the page in this order: report context, comparison controls, results heading/status, chart or table, notes/source, and actions. Keep the interface editorial rather than dashboard-like. At narrow widths, stack card controls and actions, use full-width tap targets where useful, and prevent page-level horizontal scrolling.

Completion checks:

- Tokens, not scattered literals, own repeated colors, type, spacing, radii, focus treatment, and chart constants.
- Contrast meets WCAG AA for text and meaningful controls, and focus indicators remain visible on every surface.
- Reduced-motion preferences disable nonessential transitions; no content depends on animation.
- Browser review at approximately 375 px and 1280 px widths shows no clipped controls, notes, labels, or page-level horizontal scroll.

### 7. Build the visx chart system

Implement `ChartFrame` as the shared owner of responsive bounds, margins, x/y scales, tick generation, horizontal grid lines, axes, clipping, direct-label space, tooltip positioning, legend/key, accessible description, and the source/note region. Use `ResizeObserver` through visx responsive utilities and keep layout calculations in pure helpers so they can be unit tested without SVG rendering.

Port only relevant renderer-agnostic ideas from the reference `toPlotly.js`: safe tick increments, number formatting, axis margin budgeting, title/label wrapping, legend label fitting, and responsive footnote height. Grouped categorical-section math is intentionally out of scope because this product renders temporal line series only. Preserve PPIC conventions of 2 px data lines, 1 px axes/grids, no vertical grids, restrained gray labels, and a white plot surface. The y domain should follow a documented rule agreed during visual review; default to zero in line with the PPIC guide unless doing so makes the historical/projected variation materially unreadable, in which case use a clearly tested padded domain.

Implement `ProjectionLineChart` as a thin mark layer using visx scales and line/path primitives. Render separate actual and projected paths so missing points break lines. Use color for comparison identity, solid versus dashed strokes and explicit text for actual/projected status, and a distinct marker/segment treatment plus written note for interpolation. Add direct end labels with collision handling; retain a compact legend/key when direct labels cannot carry denominator, status, or interpolation meaning by themselves.

Build a pointer/touch tooltip from prepared points with comparison label, year, status, formatted displayed value, total population, and interpolation notice. The same information must be available in the table; do not create hundreds of mandatory SVG tab stops. Provide an SVG title/description or nearby screen-reader summary that states the selected comparisons, units, historical/projected convention, hidden comparisons, and how to access exact values.

Completion checks:

- Unit tests cover scale domains, tick choices, narrow-label layout, note height, direct-label collision handling, and line segmentation across missing points.
- Chart, tooltip, legend, accessible summary, and direct labels consume the same prepared result and formatter.
- Actual/projected and interpolated states remain distinguishable in monochrome and without relying on color.
- Pointer, touch, resize, multiple-comparison, overlap-year, empty, all-suppressed, partial-hidden, and no-value scenarios render without stale tooltips or clipped SVG.
- Playwright screenshots at narrow and wide widths are reviewed against the PPIC reference patterns; screenshots are not used as proof of numerical parity.

### 8. Implement the table, view toggle, status messaging, and CSV download

Create an explicit Chart/Data segmented toggle with `aria-pressed` or tab semantics that match its behavior. Do not render an inert hidden table to satisfy accessibility; when Data is selected, show a semantic table with a caption, scoped headers, year rows, actual/projected columns per comparison, formatted values, population metadata, and visible missing/suppressed/interpolated labels. Keep wide tables inside a labeled focusable horizontal-scroll region.

Drive chart, table, live summary, tooltip, and export from the same prepared result. Announce load failures, empty selections, and suppression summaries in a polite status region without announcing every ordinary redraw. Disable download when no visible comparison can be exported and explain the state in adjacent text or an accessible description.

After the CSV-contract approval gate is resolved, implement serialization as a pure function and keep the browser Blob/download action as a thin adapter. Escape commas, quotes, and line breaks; sort years numerically; never export suppressed values; preserve missing versus zero; and include enough metadata to interpret units, denominator, prediction status, population, and interpolation.

Completion checks:

- Table values and statuses deep-equal the prepared values used by the chart and tooltip.
- CSV tests cover multiple comparisons, both prediction statuses, percent/raw format, no data, suppression, interpolation, numeric year order, and special characters in labels.
- A Playwright download test parses the emitted file and compares it with the visible table/prepared result under the approved contract.
- Toggling views preserves comparisons, scroll-independent state, and a sensible focus target.

### 9. Complete responsive, accessibility, and failure-state hardening

Test the complete app with keyboard-only use and automated accessibility checks, then manually inspect semantics that automation cannot judge. Verify visible focus, logical heading order, control names, status announcements, table navigation, touch targets, zoom to 200 percent, color contrast, reduced motion, and meaningful reading order without CSS.

Exercise initial loading, slow loading, aborted loading, HTTP failure, malformed CSV, no matching rows, all comparisons suppressed, one of several comparisons suppressed, missing outcome points, and interpolation. Errors should name the failed stage without exposing implementation noise and should offer a useful retry or refresh path.

Completion checks:

- The core flow works at 375 × 812 and 1280 × 800, at 200 percent zoom, and with keyboard only.
- Automated accessibility checks report no serious or critical findings; any accepted exception is documented with a manual test.
- Controls and chart/table alternatives remain usable with web fonts blocked and JavaScript errors represented by the app's error boundary or load state.
- No suppressed numeric value appears in DOM text, SVG attributes intended for users, tooltip state, accessible descriptions, or downloaded CSV.

### 10. Document, deploy, and cut over

Replace the placeholder root `README.md` content with verified setup, commands, architecture, data provenance, calculation rules, accessibility behavior, and Vercel deployment instructions. Update `CLAUDE.md` commands only after they have been run successfully. Record the approved data and export decisions in project memory.

Configure Vercel to run `npm run build` and publish `dist/`. If `vercel.json` is needed, set conservative caching for the unhashed CSV and immutable caching only for Vite's hashed assets. Use a preview deployment for final review, then promote the verified build rather than rebuilding different bits for production.

Run the complete release gate against the production build: clean install, lint, type check, unit/component tests, production build, Playwright flows, parity fixture comparison, responsive screenshots, keyboard review, downloaded-CSV inspection, and a direct fetch/checksum check of the deployed dataset. Confirm that no generated build output, caches, secrets, local environment files, or `v0/` changes are staged.

Completion checks:

- The Vercel production URL loads the app and data without console, network, hydration, or mixed-content errors.
- The deployed default and representative filtered results match approved parity fixtures.
- Release notes list any intentional legacy differences, especially data location, export contract, and category options.
- Rollback is the previous known-good Vercel deployment/alias; because the site is static and performs no data writes, rollback requires no database or state migration.

## Verification matrix

The implementation is complete only when all of the following are demonstrated, not merely when the page resembles the reference project:

- **Data:** schema validation, weighted rates, valid-weight handling, total population, actual/projected grouping, every filter, both denominator modes, raw derivation, suppression boundaries, missing versus zero, interpolation conditions, year ordering, and CSV escaping.
- **Cross-surface parity:** the chart, tooltip, direct labels, accessible summary, table, and approved CSV contract all derive from one prepared result, with no independent calculation path.
- **Interactions:** default load, add, edit, remove, focus recovery, value-format change, denominator change, chart/data toggle, retry, and download.
- **Responsive UI:** at least one narrow mobile and one representative desktop viewport, plus 200 percent zoom and long labels.
- **Accessibility:** semantic controls/table, visible focus, keyboard completion, meaningful announcements, non-color status cues, reduced motion, contrast, and a complete tabular alternative to the chart.
- **Visual direction:** PPIC type hierarchy, palette, cards, controls, chart strokes, axes, grids, legends, notes, spacing, and restrained editorial layout are reviewed against the relevant read-only reference files.
- **Production:** clean npm install, lint, type check, all automated tests, production build, Vercel preview smoke test, deployed data integrity check, and an inspected production download.
